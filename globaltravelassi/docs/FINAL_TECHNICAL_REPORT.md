# Final technical report: customer launch scope

Readiness: **READY_FOR_STAGING_VALIDATION**, once the owner resolves the staging project blocker below. Production: **NOT_VALIDATED**.

Baseline commit: `5f81999` (launch preparation). The commit that contains this work is listed in the chat report, not here: a document cannot name its own commit.

## 1. Implemented

- **Customer website.** Home, services list, nine service pages (what is included, what is not promised, price on request, request and WhatsApp buttons), privacy notice, terms of use, cookie notice. Arabic (right to left), French, English. Localised titles, meta descriptions, Open Graph, language alternates, sitemap.
- **Service request.** Form for signed-in active accounts. Server-side validation. Honeypot. Rate limits per account and per hashed address (1 hour windows). One-time submission token: a double submit returns the first request. Consent and privacy notice. Confirmation page with the reference. Request-received email.
- **Reference.** Ten random hex characters (40 bits), generated by the database. Not a predictable id, and not an access token: access is by account only.
- **Documents.** Private storage. Ownership checked by Row Level Security. Size limit 10 MB. The file's first bytes are checked against the declared type (PDF, JPEG, PNG); a mismatched file is deleted and refused.
- **Admin dashboard.** Overview with statistics (total, new, in progress, pending, approved, rejected, customers; by service, by language, by lead source). Requests list with filters. Request detail with status changes, notes, documents, contact log, lead source correction (with a required reason), customer category, internal activity log, the customer's other requests, timeline. Customer list. Services and prices. Reports. CSV export with formula protection. Customer email log with retry.
- **Lead source attribution.** UTM tag, then referring site, then direct, then other. First visit only; stored in an httpOnly cookie for 30 days. Recorded on the request by the server. Corrections are logged.
- **Customer emails.** Nine transactional flows plus the two Supabase Auth flows. Localised (ar, fr, en), right-to-left Arabic layout, responsive HTML with a plain-text part, escaped values, no internal fields. Outbox with database-side deduplication. Delivery log with short error codes. Manual retry, at most five attempts. Off unless `EMAIL_DELIVERY_ENABLED=true`.
- **WhatsApp.** Click-to-chat links built from the configured number, prefilled messages, on service pages, on the customer's request page, and on the admin request page. Contact is recorded by hand. No API, no automatic messages.
- **Accounts.** Disabled accounts are refused by the server actions and by the database (requests, documents, uploads).
- **Legal.** Privacy notice, terms, cookie notice, in three languages. Make no claim about visa outcomes, success rates, partnerships or guarantees.

## 2. Removed: payment functionality

- Pages and components: admin payments page, customer payment panel, admin payment recording, admin payment table on the request pages.
- Server actions: all payment actions (`lib/actions/payments.ts`) and the admin payment actions.
- Library: `lib/payments/`.
- Customer-facing text: payment FAQ, payment sections of the marketing copy, payment in the dashboard and the login page.
- Admin: revenue and pending-payment statistics, the revenue and payment figures of the AI analytics page and its loader, the payment navigation item.
- Emails: all payment email kinds are removed from the templates and the copy. Migration 0022 refuses new payment emails at the database level. Existing log rows are kept and hidden from the admin email page.
- Database (migration 0022, forward only): payment functions dropped; customer payment view dropped; customer timeline no longer shows payment events; signed-in users lose direct access to the payment tables. **No payment row, table, history or audit record is deleted.**
- Status `payment_pending`: no longer set or offered. Any existing request with it is shown as "approved".

Tests confirm the removal: `tests/launch/whatsapp-and-payments-removed.test.ts` (no payment page, component, action or database call in the application code), `tests/db/payment-removal-crm.test.ts` (database).

## 3. Security improvements in this pass

| Item | Before | After |
|---|---|---|
| Customer inserts a pre-verified document | possible (direct API) | refused (0020, and 0023 keeps it) |
| Customer registers a document outside their request folder | possible (direct API) | refused (0020) |
| Disabled account submits requests, documents, uploads | possible | refused in the app and in the database |
| Customer picks the reference, id, dates of a request | possible | refused (column grants) |
| Uploaded file content not checked | browser type trusted | first bytes checked; mismatch deleted |
| No rate limit on requests | none | per account and per hashed address |
| Double submit creates two requests | possible | one request (unique token per customer) |
| Recorded lead source overwritten silently | possible | refused by the database unless a correction is recorded |
| Admin activity log editable | — | append-only, including for the database owner (tested) |
| Redirect target from a form (delete) | not validated | validated |
| CSV formula injection | partly handled (`=`, `+`, `-`, `@`) | also tab and carriage return |
| Owner sets "payment pending" manually | possible | refused |
| Session refresh cookie not forwarded to the page | possible stale session | fixed (regression test) |

## 8. Known limitations

- Conversion rate by lead source is not measured (no visit counting).
- Service pages for an uncatalogued service fall back to seed copy; the request form only offers services in the database.
- An unknown service slug returns a 200 status with the not-found content, because the page streams after its loading boundary. The content is correct; the status is not a hard 404.
- Email retries are manual. A pending email (outcome unknown) is never resent automatically.
- The style policy allows inline styles (`style-src 'unsafe-inline'`), documented in `docs/security/CONTENT_SECURITY_POLICY.md`.
- The Supabase Auth email templates must be pasted into the dashboard by hand.
- Document type is checked from the file's first bytes; the content of the document itself is not reviewed by software.
